REPLIT AGENT MASTER PROMPT (CMGF ROADMAP IMPLEMENTATION – PHASED)

You are the lead full-stack engineer inside this existing CMGF Replit project. Your job is to implement the Manus technical roadmap to close the gap between CMGF’s architectural vision and the current demo reality. The goal is a coherent, stable, conference-ready platform in which every visible interaction works, the platform is unified under one consistent experience, and governance transparency is made visible.

Non-negotiables:

Do not convert CMGF into an autonomous decision maker.

Preserve deterministic / governed rule logic where it exists.

If outputs are simulated, label them clearly as “Demonstration Data” or “Simulated Data.”

No predictive scoring or individual outcome prediction.

Primary objective:
Deliver a unified, stable CMGF demo that supports an end-to-end narrative:
Service Member submits request → ISR queue receives it → advisor actions recorded → audit trail viewable → aggregate analytics separated.

You must produce an implementation plan first (bulleted with checkpoints), then execute changes in small verified steps.

PHASE 1 (Week 1–2): Stabilization + Unification (highest priority)

Unify platform navigation and UX

Consolidate modules currently spread across domains/subdomains into a single coherent experience.

Implement a persistent top navigation with consistent branding and routes for:

Home / Overview

Part A: Service Member Hub (new MVP)

Part C: ISR System

Credential Sequencing Engine

Analytics Dashboard

AI Services / Governance

If full consolidation is not possible immediately, create a unified “shell” SPA that embeds/links modules in a seamless way (same nav + same design), avoiding jarring jumps.

Fix all broken elements

Remove or repair all 404s.

Every button that appears actionable must respond (even if simulated).
Examples: “View Full Case”, “Approve”, “Modify”, “Escalate”, accordions, scenario runner actions, chat responses.

Replace any “Live Data” labeling with “Demonstration Data” / “Simulated Data.”

Correct labeling + citation hygiene

Where placeholders exist, swap them for real citations where feasible (NICE / O*NET references already used in parts of the system).

If the content remains illustrative, clearly label as “Illustrative.”

Deliverables for Phase 1:

A single cohesive UI experience with working navigation.

A “broken interactions checklist” completed (no dead clicks).

Labeling pass completed.

PHASE 2 (Week 3–4): Simulation Backend + Minimum Viable Part A (Service Member Hub)
4) Build a lightweight simulation backend API

Implement API endpoints that accept scenario inputs and return deterministic but varied simulated outputs (seeded by scenarioId).

Add a realistic 1–2 second delay to simulate processing time.

Ensure outputs can be logged for audit trail.

Required endpoints (minimum):

POST /api/sm/request (create a new service member request)

GET /api/isr/queue (list pending requests)

POST /api/isr/action (approve/modify/escalate with rationale)

GET /api/audit/:caseId (retrieve audit log)

POST /api/sim/skill-translate (demo skill translation, clearly simulated)

POST /api/sim/scenario-run (scenario runner output, clearly simulated)

Implement Part A: Service Member Hub (MVP)
The MVP must support the end-to-end story:

SM profile view (mocked but realistic)

“Submit New Request” form (simple: goal domain, current status, constraints checkbox, notes)

List of submitted requests with statuses

Submitting a request places it into ISR queue automatically

Deliverables for Phase 2:

Working SM→ISR pipeline (submit request → appears in queue).

Deterministic simulated responses (same input → same output per caseId).

Basic persistence in DB (or minimal store) for cases/actions.

6) Interactive Audit Trail Explorer (highest impact)
